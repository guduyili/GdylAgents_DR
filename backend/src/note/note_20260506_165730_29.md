# 任务 4: 评测治理

请将本轮新增信息补充到任务概览中：

一、任务目标补充
围绕 2026 年 Agent 落地中的评测治理，新增聚焦四个维度：1）Agent 效果评测从静态 benchmark 转向真实场景、长时程、交互式系统评估；2）安全风险从模型内容安全扩展到工具调用、权限边界、记忆污染与环境交互风险；3）治理机制需要把政策框架映射为可验证工程控制；4）合规要求需同时覆盖 EU AI Act、NIST AI RMF 及企业审计证据链。

二、关键发现补充
1. Benchmark 不能替代真实部署评测，Agent 评测对象应从“模型能力”升级为“系统行为”。
- Brookings/CMU/UC Berkeley 2026 研讨总结明确指出：很多既有 AI 评测方法不适合会持续自主行动、与用户和环境交互、追求开放目标的 agentic AI；有效治理依赖于在接近真实部署的上下文中测量、比较系统行为。
- 价值：这意味着后续选型不能只看公开榜单分数，而要设计贴近业务流程的 scenario-based evaluation、红队演练、长时任务回放与在线监测。
- 工程含义：评测维度应至少覆盖任务成功率、轨迹稳定性、跨轮一致性、异常恢复能力、人机协作质量、外部工具副作用与业务 KPI 影响。

2. Agent 治理的核心难点不是 benchmark 稀缺，而是“测量语义碎片化”和基准治理薄弱。
- AISafetyBenchExplorer 统计了 2018-2026 年间 195 个 AI 安全 benchmark，但指出当前主要问题是 fragmentation 而不是 scarcity：
  - 195 个 benchmark 中 94 个属于中等复杂度；
  - 仅 7 个处于 Popular tier；
  - 165/195 为仅英语评测；
  - 170/195 仅提供 evaluation resources；
  - 137 个 GitHub 仓库陈旧；
  - 96 个 Hugging Face 数据集陈旧。
- 其进一步指出 accuracy、F1、safety score 等相同标签背后往往对应不同 judge、aggregation rule 和 threat model，导致跨 benchmark 横向比较容易失真。
- 价值：企业在做 Agent 评测体系时，不应直接“堆 benchmark 数量”，而应先统一指标口径、威胁模型、裁判机制和覆盖矩阵，形成 benchmark portfolio governance。

3. Agent 安全风险已从提示注入/幻觉扩展为“工具使用风险 + 权限风险 + 记忆风险 + 影子 AI 风险”的复合体。
- 结合 AIMultiple、Digital Applied、UnderDefense 等资料，2026 年的治理重点明显从 model-only 走向 system-of-systems：
  - 工具调用风险：agent 访问 ERP、浏览器、代码执行、邮件、支付等工具后，错误输出会变成可执行动作；
  - 权限与访问风险：如果 agent 身份与人类账号混用，可能放大越权操作；
  - 记忆/上下文污染：长期记忆、RAG 数据源、外部网页可能持续注入错误或恶意信息；
  - Shadow AI / agent sprawl：业务部门自行接入第三方 agent，造成资产不可见、日志不全、责任不清。
- UnderDefense 文中引用 IBM 2025 Cost of a Data Breach Report：全球平均数据泄露成本为 444 万美元，16% 泄露事件已涉及 AI-driven attack vectors；未充分部署 AI security automation 的组织平均成本 552 万美元，而充分部署者为 362 万美元。
- 价值：说明 Agent 风险管理应与 IAM、SIEM/SOC、DLP、GRC、变更管理、第三方风险治理联动，而不是停留在单点模型安全测试。

4. 合规框架正在收敛到“政策要求 + 风险框架 + 可审计控制证据”的三层结构，真正落地关键在控制可验证性。
- Digital Applied 对 2026 agent governance framework 的核心洞察是：EU AI Act 与 NIST AI RMF 定义了“应达到什么结果”，但失败通常发生在 implementation layer；纸面政策若无法映射到代码和基础设施中的可验证控制，就会在首次外部审查中暴露。
- 其提出控制真实性的三个判断问题：控制运行在何处？生成什么可供外部审查的证据？失效时谁被告警？
- 文中给出可操作示例：每一次 tool invocation 都输出结构化 trace，至少包括 user ID、tool name、input hash、authorization decision，并保留 90 天、写入 append-only store。
- 同时指出 EU AI Act 对高风险系统的广泛义务将在 2026-08-02 进入实质执行窗口；而 NIST AI RMF 虽属自愿框架，但已成为美国联邦采购、SOC 2 AI readiness narrative 和企业问卷中的事实标准。
- 价值：企业选型时应优先选择原生支持审计日志、策略执行、权限隔离、人工审批、版本化变更和证据导出的 Agent 平台，而非仅比拼功能丰富度。

5. 评测治理的最佳实践正在从“离线一次性验收”演进为“全生命周期持续治理”。
- AIMultiple 对 AI governance tools 与 MLOps/observability 市场的观察显示，主流平台能力正覆盖 deploy、monitor、manage、govern 全链路，并将 trusted AI、model risk management、compliance assessment 扩展到 generative AI 与 agentic AI。
- NIST AI RMF 的 Govern/Map/Measure/Manage 四层结构也说明：评测不是孤立动作，而是持续库存盘点、风险登记、测量、处置和退役的一部分。
- 价值：Agent 项目治理应形成闭环：上线前做风险分级和基线评测；灰度期做轨迹采样和人工复核；生产期做漂移监控、越权监控、事故演练与周期复评；下线时完成数据与权限回收。

三、建议补充：面向后续落地与选型的评测治理框架
建议建立“5 层评测治理栈”：
1）能力层：任务成功率、成本、时延、稳定性；
2）行为层：工具选择正确率、步骤合理性、长期一致性、恢复能力；
3）安全层：提示注入、越权调用、敏感信息泄露、记忆污染、错误执行；
4）治理层：日志完备性、审批门控、策略命中率、人工覆盖率、变更可追溯性；
5）合规层：EU AI Act 风险分类映射、NIST AI RMF 控制映射、审计证据包完整性。

四、对后续研究/选型的启示补充
- 若要支撑落地判断，建议后续优先补充三类信息：
  1）Agent 评测 benchmark / framework 代表性项目与指标对比；
  2）Agent 安全测试与 runtime guardrail 产品能力对比；
  3）面向 EU/US 企业客户的审计证据清单与控制模板。
- 在选型标准上，建议把“是否支持真实场景回放、工具调用审计、细粒度权限控制、持续监控和合规映射”设为一票否决项。
