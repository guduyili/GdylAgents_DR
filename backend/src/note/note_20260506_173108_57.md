# 任务 1: 技术路线

请将本轮新增信息补充到任务概览中：

## 本轮新增要点

### 1. 2026 Agent 技术路线的核心变化：从“提示词工程”转向“控制循环 + 系统工程”
- 多份资料一致指出，2026 年可用的 Agent 不再被理解为单个 prompt，而是“读取状态 → 规划 → 执行工具 → 观察结果 → 更新状态 → 循环”的控制系统。
- 这意味着架构重点从 prompt 设计转向：显式状态机、确定性 reducer、失败重试、预算控制、审批门、可观测性与评测。
- 价值：为后续技术选型建立主线——2026 Agent 的竞争焦点不是“谁更会想”，而是“谁更可控、可调试、可审计、可运营”。

### 2. 架构主范式正在分化为三条路线：工作流图范式、对话式多智能体范式、轻量/类型安全范式
- 工作流图/状态机范式：以 LangGraph 为代表，强调节点、边、条件分支、循环、审批、回放与可视化调试，适合复杂生产流程。
- 对话式多智能体范式：以 AutoGen/AG2、CrewAI 为代表，强调角色分工、协作、辩论、审查、人类在环，适合研究、报告、复杂协同。
- 轻量/类型安全范式：如 Smolagents、Pydantic AI、OpenAI Agents SDK、Claude Agent SDK，强调低样板代码、严格结构化输出、模型原生工具调用、SDK 级 tracing。
- 含义：2026 不会出现“单一统一框架”，而是围绕 dominant constraint 选型：控制优先、团队效率优先、模型生态优先、数据优先或类型安全优先。

### 3. 单智能体仍是生产主力，但其内部已演进为“复合式单 Agent”
- 尽管市场高度关注多 Agent，多个资料都隐含同一事实：多数真实生产系统先从单 Agent + 工具 + 状态机 + 审批门做起。
- 2026 的单 Agent 不再是线性问答器，而是具备：计划表示（plan-as-data）、结构化工具调用、记忆分层、回退与重试策略、策略约束与人工审批。
- 工程价值：单 Agent 路线延迟更低、token 成本更可控、调试更直接，通常是从 demo 走向 production 的第一落点。
- 可作为结论：多 Agent 更像“组织结构增强器”，不是所有任务都需要；当任务存在天然角色分工、相互审查、并行子任务时，多 Agent 才具备显著收益。

### 4. 多智能体的演进重点不是“更多 agent”，而是“更清晰的协作协议与层级记忆”
- AutoGen/AG2、CrewAI、Google ADK 等代表 2026 多 Agent 方向：角色化 agent、任务委派、审查反馈、人类介入、层级协作。
- 主要痛点也较一致：token 开销大、链路更长、上下文传递失真、调试复杂、结果不可预测。
- 新趋势不是无限增加 agent 数量，而是：
  - 采用 manager-worker / planner-executor / reviewer-writer 等少数稳定拓扑；
  - 为不同 agent 设定独立 memory scope；
  - 用共享 artifacts 代替自然语言口头传递；
  - 在关键节点加入审批、仲裁或终止条件。
- 含义：2026 多 Agent 架构从“模拟团队对话”逐步走向“受约束的分布式协作系统”。

### 5. 记忆成为一等架构模块，已从“向量库召回”升级为分层记忆系统
- 实践文章强调至少四层记忆：工作记忆（当前状态）、会话摘要记忆、任务产物记忆、长期用户/组织记忆。
- Mem0 报告进一步说明，2026 记忆已经成为独立工程学科，并出现 LOCOMO 这类长程会话记忆基准。
- 基准数据显示：
  - Full-context 准确率最高，LLM Score 72.9%，但中位延迟 9.87s、p95 达 17.12s、token 约 26,000；
  - Mem0 selective memory 约 66.9%，中位延迟 0.71s、约 1,800 tokens；
  - Mem0g 68.4%，中位延迟 1.09s；
  - RAG 61.0%；OpenAI Memory 52.9%。
- 技术含义：最优路线不是“把所有历史都塞进上下文”，而是以 selective memory 在准确率、成本、延迟之间做 Pareto 优化。
- 对系统设计的价值：记忆不只是检索问题，更是状态建模、作用域管理、隐私治理、过期策略与评测问题。

### 6. 工具调用在 2026 已经 API 化、契约化，成为 Agent 可靠性的核心决定因素
- 资料普遍强调：工具不是“建议”，而是强类型 API 合同。
- 关键工程规范包括：
  - 输入输出结构化（JSON Schema / Zod / OpenAPI / Pydantic）;
  - invalid args 机器可读报错；
  - 结果采用 `{ok, data, error, meta}` 包装；
  - side-effect 工具必须幂等，要求 idempotency key；
  - 每次调用必须带 timeout / retry / cost budget。
- 含义：Agent 的失败模式更多来自错误工具选择、错误参数、错误时机和副作用重复，而不是纯推理错误。
- 可作为任务报告中的关键判断：2026 Agent 能否进入核心业务，首先取决于 tool contract 设计成熟度，而不是模型 benchmark 排名。

### 7. 运行时（runtime）正在成为 Agent 基础设施的新战场
- 从多份框架比较可以抽象出统一 runtime 诉求：状态持久化、图执行、分支与循环、重放、审计日志、人工审批、隔离执行、任务队列、预算管理、追踪与回溯。
- LangGraph 被反复强调适合复杂 branching/retry/human approval；Dify/Flowise 偏产品化与低代码；Semantic Kernel 偏企业集成；OpenAI Agents SDK 与 Claude Agent SDK 则强化模型原生 runtime 能力。
- 这表明 2026 技术路线的关键问题已经从“怎么把 LLM 接进来”转为“如何给 LLM 提供安全、可回放、可治理的执行环境”。
- 工程价值：运行时层会决定 SLA、调试效率、跨团队协作、成本治理与安全边界，是框架选型中最容易被低估、却最难后补的部分。

### 8. Evals、Tracing、Guardrails 已从辅助组件升级为生产必选项
- Andrii 的实践指南明确指出：没有 trace 就无法调试；没有 trajectory-level eval 就无法真正评估 agent；没有 policy-as-code、审批和注入防护就无法安全上线。
- 2026 评估从“最终答案是否正确”升级到“整条轨迹是否正确”：是否选对工具、参数是否正确、是否遵守预算与策略、是否在正确时机请求人工批准。
- Alice Labs 也强调 observability 要与框架一起选：如 LangGraph + LangSmith，CrewAI/Pydantic AI + Langfuse，Semantic Kernel + Azure Application Insights。
- 含义：评测与观测正像 CI/CD 一样成为 Agent 工程的默认基建，而不再是上线后的补丁。

### 9. 生态演变：2025→2026 的主线是“框架碎片化加剧，但底层能力开始收敛”
- 碎片化：LangGraph、CrewAI、AutoGen/AG2、Semantic Kernel、LlamaIndex、Pydantic AI、OpenAI Agents SDK、Claude Agent SDK 等各自占据不同最佳场景。
- 收敛点：几乎所有框架都在补齐同一套能力——工具调用、记忆、状态、工作流/多 agent 编排、HITL、可观测性、评测、护栏。
- 关键历史事件包括：
  - AutoGen 与 AG2 分叉，说明多 agent 社区仍在快速重构；
  - LangGraph 从 LangChain 抽象中强化为生产级状态图；
  - Claude Agent SDK 和 OpenAI Agents SDK 代表模型厂商开始向“官方 agent runtime”下沉；
  - Pydantic AI 反映出开发者对类型安全、可测试性的需求上升。
- 结论价值：未来竞争未必是“哪家框架全能”，而更可能是“谁能在标准化工具协议、模型上下文协议、观测与部署层形成事实标准”。

### 10. 对“2026 Agent 技术路线”可归纳的高价值判断
- 核心技术模块不再彼此孤立，而是形成依赖链：模型能力 → 计划/决策 → 工具契约 → 状态机/运行时 → 记忆 → 观测评测 → 护栏治理。
- 从架构演进看，最稳妥的路线不是一步到位上复杂多 Agent，而是：
  1) 单 Agent + 严格工具合同；
  2) 显式状态机 + tracing + evals；
  3) 分层记忆；
  4) 审批门与 guardrails；
  5) 再按角色需要引入多 Agent。
- 这一路线兼顾成本、可控性、上线速度与后续扩展性，适合作为任务“技术路线”章节中的推荐演进路径。
