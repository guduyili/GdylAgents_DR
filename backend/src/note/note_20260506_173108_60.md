# 任务 4: 评测安全

请将本轮新增信息补充到任务概览中：

任务总结

1. 评测体系正在从“单轮问答准确率”转向“系统级、生命周期化评测”，尤其适用于智能体。
- 含义：面向 2026 的 agent 评测不再只看模型回答是否正确，而是要覆盖任务成功率、长任务稳定性、工具调用正确性、第三方 API 连接点、人机协同流程（HITL）、上线后监控反馈等全链路行为。Tredence 明确指出 AI red teaming 的 scope 已扩展到训练/微调数据管道、推理输出控制、第三方工具/API 连接、HITL 决策流和部署后监控。
- 价值：这意味着企业若仍用传统 NLP benchmark 或单点离线测试来评估 agent，很容易漏掉“工具执行正确但业务结果错误”“长链路任务中途漂移”“多系统耦合触发 emergent behavior”等关键失败模式。对采购、验收和生产运营而言，应建立“离线能力评测 + 在线任务评测 + 安全对抗评测 + 运行时监控”的四层体系。
- 工程启示：建议把任务成功率拆成 end-to-end success、子步骤成功率、工具调用成功率、人工接管率、重试率、回滚率、平均完成时长、超时率等多维指标，而不是只给一个 aggregate score。

2. 红队评测已成为 agent 安全治理核心，不是附属测试项，而是标准化采购与治理能力。
- 含义：OWASP GenAI Security Project 已将 Red Teaming & Evaluation 作为独立工作流，目标是建立标准化方法论、benchmark、tools、frameworks；并发布《Vendor Evaluation Criteria for AI Red Teaming Providers & Tooling v1.0》。同时，OWASP 在 2025 年底发布 Agentic Applications Top 10 与对应风险缓解指南，且官方说明其结论汇聚了 100+ 行业专家输入。
- 价值：这表明市场正在从“有没有做红队”转向“红队服务是否可比较、可审计、可复现、可治理”。对于企业而言，选择供应商时不能只看攻击样例数量，而要看是否支持 threat modeling、证据留存、复现实验、修复验证、覆盖 agent-specific 风险（prompt injection、上下文污染、权限滥用、工具链攻击、数据泄露、偏见/合规风险）。
- 对比视角：传统渗透测试关注基础设施、应用接口、身份边界；AI red teaming 更强调行为层与语义层攻击，如 context manipulation、emergent behavior、misuse scenario 和 policy circumvention。两者需要结合，不能互相替代。
- 优缺点：红队优点是贴近真实对抗与业务风险；缺点是成本高、样本不完备、结果容易依赖测试者经验，因此需要标准化场景库和持续化执行，而不是一次性项目。

3. Agent 安全风险的本质正在从“内容风险”升级为“权限风险 + 行动风险 + 供应链风险”。
- 含义：多份材料都强调 agent 已从“回答问题的助手”变成“网络中的自治行为体”。Practical DevSecOps 直接将 AI agents 描述为一种新型 insider threat；Tredence 指出独立行动（independent action）会放大错误与策略违规；OWASP 和 AccuKnox 则把 MCP、安全连接点、AIBOM、供应链透明度、Prompt Firewall、AI-DR、Agentic AI Security 等纳入框架。
- 价值：因此评测安全不能只测模型是否“说错话”，更要测它“会不会错误地做事”。例如：是否会在被诱导时越权读取数据、调用高危工具、触发外部付款/删除/发布操作、跨租户泄露上下文、把敏感数据发送给未批准 AI 服务，或被恶意 MCP server/第三方插件污染决策链。
- 工程实践：应采用最小权限、分级授权、工具 allowlist、审批门控、双人复核、高风险动作 sandbox、敏感操作 step-up authentication、会话级和任务级令牌隔离。对 agent 的评测数据集也应引入“权限挑战集”，专门测试其在模糊授权、角色切换、诱导升级中的行为。
- 历史演变：早期 LLM 安全更重 jailbreak、toxicity、hallucination；agent 时代则把执行权限、环境接口和供应链安全推到一线，安全边界从 prompt 扩展到 tool/runtime/integration/governance。

4. 审计与合规控制正在成为评测体系的硬约束，尤其要求持续可追溯和可证明。
- 含义：AccuKnox 明确指出，到 2026 年治理已从“建议项”变成“强制项”，需对齐 NIST AI RMF、ISO/IEC 42001、EU AI Act，并强调 continuous controls 与 auditability。OWASP AIBOM Generator 则体现了 AI 供应链透明化方向，即不仅要知道模型结果，还要知道模型、数据、组件、依赖和连接关系。
- 价值：这意味着企业不能只展示“模型平均表现不错”，还要能够回答：谁授权了该 agent？它调用了哪些工具与模型？其训练/部署链路用了哪些数据和组件？高风险输出是否可追溯到提示词、上下文、工具响应和决策节点？修复后是否完成再验证？这些能力决定了是否能通过内审、监管和客户尽调。
- 工程落地：建议建立 agent 审计日志最小字段集：任务 ID、用户/代理身份、上下文摘要、提示模板版本、检索文档版本、工具调用序列、权限决策、人工接管记录、输出版本、异常告警、策略命中、回滚/终止原因。并将评测结果纳入 GRC 证据链，而非仅存在测试报告里。
- 优缺点：强审计有助于问责、复盘和合规，但会带来存储、隐私和性能成本；因此需要对日志做脱敏、分级留存和访问控制。

5. 2026 年值得采用的评测方法论不是单一 benchmark，而是“能力评测 × 韧性评测 × 治理评测”三轴模型。
- 含义：结合现有材料，可把 agent 评测抽象为三条主轴：
  1) 能力轴：任务成功率、工具正确率、长任务完成率、恢复能力、成本/时延；
  2) 韧性轴：对 prompt injection、上下文污染、恶意工具输出、数据泄露、越权操作、异常连锁反应的抵抗力；
  3) 治理轴：审计可追溯、权限控制、人工干预、供应链透明度、合规映射、修复闭环。
- 价值：这一模型的创新点在于把“好不好用”和“安不安全/能不能管”统一成同一个决策框架。很多 agent 在 demo 中能力强，但一旦加上权限约束、审批流、审计记录后，成功率和延迟会显著变化；只有三轴一起看，才接近真实生产表现。
- 实践建议：企业可以建立分级验收门槛，例如 POC 阶段看能力轴，灰度阶段增加韧性轴，生产准入必须满足治理轴最低控制基线。最终形成“先测能力，再测破坏，最后测合规可运营”的递进式方法。
- 局限性：三轴模型的难点在于跨团队协同，需要安全、平台、法务、业务共同定义阈值；但这恰恰是 agent 从实验走向企业级部署的必要过程。
