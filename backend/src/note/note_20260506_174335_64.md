# 任务 4: 产品生态

请将本轮新增信息补充到任务概览中：

## 新增关键发现

1. **2026 年 Agent 产品生态已形成“厂商原生 SDK + 独立开源编排框架 + 协议/连接层 + 企业平台”四层结构，选型不能只看框架本身。**
   - Morph 的 2026 框架对比指出，主流代码优先框架至少覆盖 8 个核心选项：Claude Agent SDK、OpenAI Agents SDK、Google ADK、LangGraph、CrewAI、Smolagents、Pydantic AI、AutoGen / Microsoft Agent Framework。
   - StackOne 将整个市场进一步扩展为 **120+ 工具、11 个类别**，说明“Agent 框架”只是其中一层；真实生产栈还包含 observability、memory/vector DB、tool integrations、protocols、AI IDE、enterprise platform、AI cloud 等。
   - 含义：企业如果只比较“哪个框架更火”，很容易低估后续在连接器、治理、评测、部署上的重构成本。
   - 价值：为本任务的“产品生态”建立了分层视角——后续比较厂商时应按“模型/SDK/协议/平台/基础设施”拆分，而不是将所有产品放在同一维度横向比较。

2. **生态竞争的主轴已经从“谁有 Agent”转向“谁能控制协议与集成入口”；MCP 成为事实上的工具互联底座，而 A2A 仍处于更高层协同阶段。**
   - Morph 提到 **MCP 已有 200+ server implementations**，并指出 Claude Agent SDK 的 MCP 集成最深；OpenAI Agents SDK 也已 adopted MCP；CrewAI 原生支持 MCP；Google ADK 多通过 adapter 接入。
   - Augment 的 2026 分析则给出更强工程信号：**PulseMCP 目录已有 10,000+ published servers**，且主流 IDE（VS Code、Cursor、Claude Code、JetBrains AI Assistant）均原生支持 MCP；相比之下，**A2A 尚无主流 IDE 原生落地产品**。
   - 同时协议层正在收敛：Morph 指出 **ACP merged into A2A under the Linux Foundation**，意味着 agent-to-agent 通信标准在整合，但其应用成熟度仍明显弱于 MCP。
   - 含义：MCP 解决“让单个 agent 能调用外部工具”的接入问题；A2A/ACP 解决“多个 agent 跨进程/跨厂商协作”的编排问题，二者不是替代关系，而是分层互补。
   - 价值：选型顺序应优先考虑 MCP 兼容性与工具覆盖率，再决定是否需要 A2A；这对多数 2026 年仍处于单 agent/弱多 agent 阶段的团队更具 ROI。

3. **厂商原生框架与独立开源框架的边界正在清晰化：前者赢在深度能力与默认体验，后者赢在模型灵活性与体系中立。**
   - Morph 将生态明确划分为两类：
     - **Provider-native SDKs**：Claude Agent SDK、OpenAI Agents SDK、Google ADK；
     - **Independent frameworks**：LangGraph、CrewAI、Smolagents、Pydantic AI、AutoGen。
   - 原生 SDK 的代表能力边界：
     - Claude Agent SDK：内建文件系统与 shell、hooks、subagents、最深 MCP 集成，适合 coding / research / OS-level agent，但被锁定在 Claude 模型；
     - OpenAI Agents SDK：以 handoff、guardrails、tracing 为核心，适合轻量 handoff chain；
     - Google ADK：支持 **Python / TS / Java / Go 四语言**，原生强调层级式多 agent 与企业多语言环境。
   - 独立框架的差异化：
     - LangGraph：显式图/状态机，适合高控制、可恢复、可插入人工审核的工作流；
     - CrewAI：角色化协作，上手快，适合快速原型和业务分工型 agent；
     - Smolagents：强调“写代码而不是 JSON tool calling”，适合本地开源模型；
     - Pydantic AI：偏类型安全和结构化输出，不是典型多 agent 框架；
     - AutoGen / MS Agent Framework：擅长会话式多 agent 与 human-in-the-loop。
   - 含义：原生框架更像“最佳实践打包”，独立框架更像“可移植的 orchestration runtime”。
   - 价值：如果组织已明确押注 Claude / OpenAI / Google 某一模型族，原生 SDK 可显著减少工程样板；若组织需要跨模型、跨云、跨合规区部署，则独立框架更具长期可迁移性。

4. **多 Agent 并非默认优选，真正的工程瓶颈往往在上下文、工具清单膨胀与治理，而不是“缺少更多代理”。**
   - Augment 揭示了 MCP 在生产中的一个核心成本：工具 manifest 会注入上下文窗口，12 个 MCP servers 可带来 **约 81,986 tokens** 的初始工具上下文；Atlassian 报告大型 MCP server 的工具描述可能消耗 **10,000–30,000+ tokens / request**。
   - Anthropic 的 code-execution pattern 据称可将 **150,000 tokens 降到约 2,000，压缩 98.7%**，说明“通过代码与工具交互”是抑制工具膨胀的重要工程策略。
   - Promethium 也指出，多 agent 系统进入生产后会暴露类似微服务系统的问题：级联失败、资源争用、上下文不同步、治理盲区、成本不可见、调试复杂度指数上升。
   - 含义：从单 agent 升级到多 agent，不是能力自然增强，而是把 orchestration、共享上下文和分布式治理问题前置了。
   - 价值：选型时应优先问“是否真的需要多个自治 agent 并行协作”，而不是默认堆叠 agent 数量。对很多业务，单 agent + scoped MCP + workflow graph 可能比多 agent conversation 更稳、更便宜、更易调试。

5. **企业级生态正在向“集成与治理平台化”演进，框架选型越来越受数据版图、组织技术栈和合规要求驱动。**
   - StackOne 提供了一个典型连接层信号：其平台宣称 **10,000+ actions spanning 200+ connectors**，说明企业真正购买的往往不是“LLM 推理能力”，而是标准化 SaaS/系统动作访问能力。
   - Promethium 指出，2026 年企业多 agent 平台开始分化为：
     - **垂直一体化数据平台**（如 Snowflake、Databricks、Microsoft Fabric）；
     - **purpose-built agentic platforms**；
     - **开放式 agent/data fabric 架构**。
   - 其核心分歧在于：数据是集中到统一平台中治理，还是保持分布式，通过开放连接与统一语义层访问。前者治理更强，后者迁移更灵活。
   - Alice Labs 的生产经验也强调：真正决定上线成败的，经常不是框架而是 observability、guardrails、evaluation 与 deployment，且建议“框架与观测栈一起选”，例如 LangGraph 搭配 LangSmith、CrewAI/Pydantic AI 搭配 Langfuse、Semantic Kernel 搭配 Azure Application Insights。
   - 含义：企业 Agent 生态的竞争壁垒，正在从“prompt/orchestration 抽象”迁移到“谁能把连接器、安全、审计、观测、数据权限和部署方式打通”。
   - 价值：本任务后续若要给出选型建议，应把“组织既有技术栈/数据位置/安全边界/运维能力”纳入决策矩阵，而不是仅比较开源 star 数或单点功能。

## 可直接用于后续报告的初步选型框架

- **押注单一模型厂商、追求最快落地**：优先看 Claude Agent SDK / OpenAI Agents SDK / Google ADK。
- **强调跨模型与流程控制**：优先看 LangGraph、Semantic Kernel、AutoGen/AG2。
- **强调快速原型与角色分工**：优先看 CrewAI。
- **强调类型安全或结构化输出**：优先看 Pydantic AI。
- **强调本地开源模型 / 代码生成式工具调用**：优先看 Smolagents。
- **先做工具互联**：MCP 优先级高于 A2A；A2A 适合成熟多 agent 系统后补。
- **进入企业生产前必须补齐**：observability、eval、guardrails、connector governance、token/context management。
