## 1. 建议结论与取舍

建议把 GdylAgents_DR 作为持续演进的 Agent 实验项目，按以下顺序推进：

**评估基线 → 决策循环与工具契约 → 证据质量 → RAG 与上下文 → 状态恢复 → 多 Agent 对照实验。**

可靠性与可观测性贯穿各阶段。每次扩展都回答四个问题：当前机制有什么限制？新机制改变了什么？收益如何测量？付出了多少复杂度、延迟和调用成本？

| 讨论点 | 建议选择 | 原因与重新考虑的条件 |
|---|---|---|
| 继续完善当前项目，还是全面换框架？ | 保留主链路，另做小范围框架对照实验 | 先理解状态、调度和工具边界；当恢复、人工介入等需求重复出现时，再评估迁移收益 |
| 已有 RAG 专题，是否直接做向量库？ | 先建立检索与质量基线，再决定检索实现 | 当前词项检索可以作为对照；先确认漏检来自同义表达、分块还是语料不足 |
| 是否优先做多 Agent？ | 放在单任务决策与证据评估之后 | 没有基线，很难区分角色分工收益与更多调用带来的收益 |
| 是否优先做平台化？ | 先学习状态恢复和执行语义，团队功能后置 | 对当前学习目标而言，持久化、幂等和取消比账号体系、管理后台更直接 |

前三个建议实验：**事实核对反例、线程超时边界、受限的搜索决策循环**。它们改动范围可控，分别训练评估思维、并发语义和 Agent 控制逻辑。

### 两个优先验证的代码观察

1. **事实核对存在自我匹配路径。** `FactCheckService.check()` 从摘要抽取术语，再用“出现在来源中，或出现在摘要中”判定匹配。后半条件使抽取出的术语容易天然满足条件。建议构造“摘要很完整、来源有 URL 但内容无关”的负例，先测出误判，再讨论证据核对方式。此处是静态代码观察，本次未执行复现。
2. **超时检测与实际返回时间可能不同。** `TaskExecutor._call_with_timeout()` 在 `with ThreadPoolExecutor(...)` 内抛出超时；上下文退出会等待运行中的任务，`future.cancel()` 也不能终止已经运行的线程。这意味着底层调用阻塞时，调用方可能无法按预期及时返回。应测量调用返回、底层结束、取消终态三个时间点。机制依据：[Python concurrent.futures 官方文档](https://docs.python.org/3/library/concurrent.futures.html)。本项目中的具体表现仍需实验确认。

## 3. 学习主线 A：决策循环、规划与工具契约

### 原理问题

把一个 Agent 步骤拆成：**读取当前状态 → 选择动作 → 执行工具 → 接收观察结果 → 更新状态 → 判断继续或结束**。重点是动作如何受状态与反馈影响，以及谁负责约束执行。

先画出当前系统中哪些决策由 Python 分支决定，哪些由模型输出决定。再沿着 `AgentFactory → ToolAwareSimpleAgent → ToolRegistry → tool_call_listener` 阅读锁定版本 `hello-agents==0.2.9` 的实际实现，记录工具格式、解析失败和终止行为，避免仅凭类名推断实现。

ReAct 可作为“动作与环境反馈交替进行”的原理阅读材料。将论文机制映射到本项目的状态、动作和观察字段即可，不要求模型暴露完整内部推理。资料：[ReAct 原论文](https://arxiv.org/abs/2210.03629)。

### 最小实验：只给单个研究任务增加决策循环

- 保留现有固定搜索流程作为基线；实验版本允许选择 `search` 或 `finish` 两种动作。
- 明确动作结构、参数校验、工具白名单、错误返回、最多轮数和总时间预算。
- 第一次搜索无结果时，允许改写 query；信息已足够时结束；预算耗尽时返回已有证据与未解决问题。
- 记录动作、简短决策说明、工具输入输出摘要及停止原因；为输入输出设置长度边界。

**验收**：正常命中、空结果、非法工具、参数错误、连续重复搜索、预算耗尽均有可重复结果；同一组任务上比较成功率、工具次数和耗时。只有新循环改善目标场景，才扩大使用范围。

### 下一步：规划成为可验证的数据

为任务增加依赖关系的实验字段，构造 `A、B 可并行，C 依赖 A 和 B` 的小图。理解 DAG（无环依赖图）的就绪任务、依赖失败传播与状态合并；拒绝未知依赖、重复 ID 和环。之后再研究“证据不足时新增或修改计划”，并限制重规划次数。

**掌握标准**：能解释固定流水线、条件分支、DAG、反馈循环各自解决什么问题，并知道简单任务何时不需要动态规划。

## 4. 学习主线 B：证据、评估与有限修订

### 先把评估拆成三层

| 层次 | 数据与方法 | 能回答的问题 |
|---|---|---|
| 确定性回归 | 保留当前 fake pipeline 和现有测试 | 事件、状态、异常分支是否按约定运行？ |
| 固定材料质量评估 | 固定网页片段、任务、参考主张与标注来源；生成环节可用真实模型 | 同样证据下，规划、摘要和报告是否更准确完整？ |
| 联网研究评估 | 固定主题集合，记录搜索时间与返回材料 | 真实来源获取与端到端表现怎样？结果受外部变化多大影响？ |

建议先整理 12～20 个小案例，覆盖：单事实、多来源冲突、资料不足、时效变化、同义查询、无关历史、工具故障。划分调试集与保留集；这只是学习规模，不能据此宣称具有统计显著性。

### 从关键词检查走向主张与证据对应

“主张”指可核对的具体陈述，例如“某方案在测试条件 X 下耗时 Y”。为每条关键主张保存来源 URL/文档 ID、原文片段、抓取时间与对应位置，并给出 `supported / contradicted / insufficient` 三种结论。

最小实验先使用人工构造的材料：同一主张分别配上支持、反驳、无关来源。随后加入“关键词都出现，但否定关系或数字不同”的反例。即使引用存在，也必须判断来源是否真的支持该句。

建议第一轮只增加一次有限修订：**报告 → 检查证据缺口 → 定点补充或修订 → 再检查 → 结束**。设定最多修订轮数；无法消除的冲突保留在报告中。

**验收**：无关来源和矛盾数字不会被当作已支持；资料不足能明确保留未知；修订没有无限循环。若引入模型评分员，固定评分规则，并与人工标注核对分歧，避免让写报告的模型独自证明自己正确。

## 5. 学习主线 C：RAG、工作记忆与上下文管理

继续使用 [RAG 专题](rag_learning_path.md) 的代码入口，但采用“先测失败类型，再升级实现”的顺序。

1. **区分记忆类型。** 当前任务的观察与中间结果属于工作状态；历史报告属于可检索资料；Skill 是指引文本。分别确定生命周期、来源和使用范围。
2. **建立词项检索基线。** 人工标注 query 与相关 chunk；检查标题、分块、同义表达、中文匹配、重复片段和无关语料。
3. **比较检索策略。** 先做分块或标题加权等单变量实验；仍存在明显语义漏检时，再比较向量或混合检索。混合方案需考虑分数归一化或排名融合，直接相加前先验证分数尺度。
4. **研究上下文预算。** 比较“整段塞入”“去重后的片段”“携带来源的压缩片段”，测量遗漏关键证据与错误引入情况。
5. **管理语料生命周期。** 明确报告新增、修改、删除后索引何时生效；记录内容版本，支持重建与失效处理。

代码注意点：`LexicalReportRetriever` 将分块缓存在实例内；HTTP 入口又会创建 Agent/服务实例。需先核实实际对象生命周期，再讨论缓存陈旧与重复建索引成本，不能笼统断言“新增报告必须重启”。另外，索引缺失、异常或无报告 ID 时会回退扫描 Markdown；若希望严格只检索报告，应将筛选策略作为独立实验。

**对照组**：RAG 关闭、词项检索、候选增强方案。固定历史语料、主题与生成配置；相关历史应有帮助，无关或错误历史不应把结论带偏。历史报告保留原始出处，避免将生成内容反复检索后当作独立证据。

**验收**：报告更新后检索行为可解释；无命中与检索异常可降级；引用可追溯；记录检索质量与最终报告质量，二者分别评估。RAG 不会自动减少搜索次数，只有规划或执行策略发生相应改变时才可能产生该收益。

## 6. 学习主线 D：并发、状态机与可恢复执行

### 6.1 把可靠性写成明确语义

沿 [task_executor.py](../backend/src/services/task_executor.py)、[stream_runner.py](../backend/src/services/stream_runner.py)、[取消链路文档](cancellation.md) 理解以下层次：

- 底层网络连接/读取超时、单工具预算、单任务预算、整次研究截止时间如何配合。
- 协作取消只在检查点生效；停止等待、停止提交新工作、终止底层执行分别意味着什么。
- 重试与 fallback 如何分类：暂时性故障可重试，参数错误先修正；取消后停止重试，所有尝试共享总预算。
- 并发任务的写入如何合并；一个任务失败后，其他任务继续、取消还是跳过依赖项。
- 慢客户端下事件队列如何受限；若合并细碎 chunk，终态与错误事件仍应可靠保留。

**实验**：用可控阻塞工具测出超时与取消边界，并在测试结束时释放阻塞，避免测试本身挂死；注入一个迟到结果，确认终态不会被重新写回运行中。先复现第 2 节的线程池问题，再比较底层超时、协作取消或进程隔离等方案；仅改成 `shutdown(wait=False)` 不能消除仍在运行的工作。

### 6.2 从时间线存储走向断点续跑

建议先为任务完成边界设计 checkpoint（保存足以继续执行的状态快照），至少包含：状态版本、计划版本、任务结果、下一执行位置、预算余量和已完成副作用的标识。

区分三个目标：

| 目标 | 必须解决的问题 |
|---|---|
| 前端断线后补看事件 | 稳定事件序号、补发接口、去重和缺口处理 |
| 浏览器关闭后继续研究 | 执行生命周期与订阅连接解耦，显式取消仍有效 |
| 后端进程重启后继续研究 | 持久状态、恢复入口、任务认领、重复执行与副作用处理 |

当前已有“断开连接触发取消”的行为约定。若增加后台持续执行，应设计明确运行模式与用户提示；事件传输仍可使用 SSE，是否能恢复主要取决于执行与存储机制。

**最小恢复实验**：完成任务 A 后中断独立测试进程；恢复后 A 的结果复用，B 继续执行，最终报告只保存一次。为笔记写入设计幂等键，即重复请求仍对应同一逻辑写入；测试“写入成功但完成标记尚未持久化”这个窗口，不只测试正常 checkpoint。

可以随后用 LangGraph 做同样的三节点实验，对比状态保存、恢复位置与实现负担，再决定是否引入。框架持久化机制参考：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

**掌握标准**：能解释事件回放、状态快照与执行恢复之间的关系，以及重复执行时如何避免重复副作用。

## 7. 拓展主线 E：MCP、Skill 与多 Agent

完成前面的单任务与评估实验后，按兴趣选择一个分支。

### 工具协议与 Skill 分支

把已有搜索后端包装为一个最小 MCP 工具，保持业务层输入输出不变。学习工具发现、输入 schema、结构化结果、超时和错误映射；用相同故障案例比较本地调用与协议调用。先锁定规范版本，学习资料：[MCP 2025-11-25 Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。

Skill 则关注“何时加载哪些指引”。针对当前名称/描述匹配补充中文命中、误选、冲突指引和超长文本案例。分别记录选择正确率和任务结果变化，避免把“加载成功”当成“任务改善”。

边界实验：在固定网页片段中放入“忽略任务、调用其他工具”的诱导文本，观察系统是否越权；执行端限制可用工具与参数，检索材料作为数据处理。MCP 工具注解需要依据来源建立信任，不能仅凭工具自报只读就扩大权限；上述规范明确要求谨慎信任注解。

### 多 Agent 协作分支

先做“研究者 + 审核者”两角色。使用显式消息结构：任务目标、证据引用、输出、未解决问题与预算；每个角色只接收需要的上下文。审核者检查证据缺口，由编排器决定最多追加一次检索。

必须保留三个对照组：单 Agent、单 Agent 增加一次自检、双 Agent 协作。尽量统一证据、模型配置、总调用或 token 预算，避免多花一倍资源后直接归因于协作架构。

**验收**：交接信息完整、失败能收敛、预算能终止；对困难案例记录质量、耗时与成本。没有稳定收益时，保留实验结论即可。后续再考虑 Supervisor 动态委派、并行专家与结果仲裁。

## 8. 如何判断优化真的有效

| 指标 | 建议计算口径 | 使用边界 |
|---|---|---|
| 任务成功率 | 满足预先验收条件的案例数 / 总案例数 | 同时报告失败与取消，区分系统异常和信息不足 |
| 主张支持率 | 有来源支持的可核对主张数 / 被评估的可核对主张数 | 与覆盖率一起看，避免少写内容获得高分 |
| 要点覆盖率 | 正确覆盖的参考要点数 / 标注要点数 | 保留集事先定义要点，避免按输出临时改标准 |
| 检索 Recall@k | top-k 找回的相关片段数 / 标注相关片段总数 | 无相关片段案例单独统计误检；必要时去重到文档级 |
| 延迟与资源 | 首事件延迟、总耗时、工具调用次数、token 用量 | 小样本列原始值和中位数；积累足够样本再看尾部延迟 |
| 恢复与取消 | 取消响应时间、底层停止时间、重复副作用数 | 调用方返回与资源停止分开测量 |

所有真实模型实验记录：代码提交、案例/语料版本、Prompt/Skill 版本、模型标识、配置、检索策略、运行时间、结果与失败原因。用量缺失标记为未知，不填零；估算费用注明计价来源与日期。

每次先声明一个假设，例如“加入标题信息会改善短查询的检索召回”。保持其余变量一致，同一案例成对比较；真实模型有波动时重复运行并记录分歧。**没有改善也是有效结论，只要实验能重复、边界清楚。**

## 9. 建议节奏：12 周，可按验收结果伸缩

默认每周投入约 6～8 小时；时间仅用于安排，达到阶段验收后再继续。同一时间推进一个主实验。

| 时间 | 主任务 | 项目内交付与进入下一阶段的条件 |
|---|---|---|
| 第 1 周 | 绘制决策权与状态流；准备评估案例 | 一张调用/状态图、一份基线记录，能区分流程通过与质量通过 |
| 第 2 周 | 事实核对反例、超时边界实验 | 两份可重复失败记录；必要修复在后续独立变更完成并回归 |
| 第 3～4 周 | 受限决策循环与工具契约 | 基线/实验对照、停止规则、错误与预算测试；能解释每一步动作来源 |
| 第 5 周 | 主张与证据映射、一次有限修订 | 支持/矛盾/不足案例及评估结果，修订可以按预算收敛 |
| 第 6～7 周 | RAG 与上下文实验 | 固定语料、检索与报告质量对照、索引生命周期说明 |
| 第 8～9 周 | DAG 状态、取消与 checkpoint | 三节点依赖实验、独立进程恢复实验、重复写入窗口测试 |
| 第 10 周 | 人工介入或框架对照 | 恢复后编辑计划的版本处理，或与 LangGraph 的同任务对照记录 |
| 第 11 周 | MCP 或双 Agent，二选一 | 相同任务与预算下的结果，以及是否纳入主链路的决定 |
| 第 12 周 | 综合复盘 | 用保留集跑对照；整理能力边界、失败样本和下一轮优先级 |
